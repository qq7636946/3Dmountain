## 原因：為什麼審計的「racing line」不夠，改成什麼

河道在 p 5.6–5.9、7.4–7.6、8.6–8.9 轉彎，是連續的 S 形（航向 +36° → −48° → +47° → −26°），每個擺幅只有 0.9–1.2 個旅程單位，平均 65–80°/單位，尖處 185–229°/單位。滾輪 0.74 單位/秒 → 峰值 155–170°/s。

審計的做法（中線往內側抄近路，夾在 ±0.45 河寬內）實測**幾乎沒效**：用高斯平滑＋夾制、再用交替投影求出走廊內最平順的路徑，航向變化率峰值只從 230 降到 212–225°/單位，因為 ±0.45 河寬（約 ±7–9 單位）相對於轉彎半徑（約 70）太窄。位置本身救不了，要處理的是**視線方向**。

本版（`prototypes/index1-5/canyon-racing.js`，純函數、表在載入時建、調 dial 時 ~1 ms 重建）：
1. **YAW**：在舊視線（看前方 29 單位的弦）上加一個修正角 x(s)，使視線轉向速度 ≤ CAP（.7 → 60°/單位）。解法是精確的可行性掃描（區間傳遞，前向＋後向）：x 在飛行起點與每個停點（容差 ±1.5–2.5°）回到 0；舊視線在不需要時完全不動；之後用只作用在偏離處的高斯柔化讓轉向緩入緩出（速度不會超過上限）。
2. **SIDE**：視線落後河道多少，鏡頭就往彎內側滑多少（−0.27 單位／度），軟夾在 ±0.45 河寬內，永遠在水面上。
3. **ROLL**：側傾跟著鏡頭自己的轉向速度，並提早 0.18 單位（約 0.25 秒）進入；繞視線軸滾（不是繞河道切線）。
4. **ALT**：河道開闊處升高、狹窄處降低（不低於 2.0）；起點 0.4 單位、停點 ±0.25 單位內淡出，停點回到 2.4。
5. **B-19**：轉彎側向模糊用 main 的一個小 patch（不改共用 js）：在 `canyonMotion.measure()` 之後，把快門位移與光點共用的 `shiftWorld` 在鏡頭右向的分量乘上 `lateralBlur`（預設 .5）。直道本來接近 0，所以直道不變。

物理上的代價（誠實）：停點落在 S 彎的擺幅中間，平均擺幅速率（78°/單位）高於上限 60，所以視線必須「少轉一點」——最大偏離河道方向約 **+32° / −24°**（出現在擺幅端點，約 0.2–0.4 單位）。畫面上是鏡頭像無人機一樣提早看向出口、略為落後於彎尾，河道 S 形會斜斜穿過畫面；導光束（follow lights）在這些位置也呈 S 形。調弱用 `彎道取直`（.5 時 yaw 偏離 ≤17°，峰值約 86°/s）。
